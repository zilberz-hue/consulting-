# טייזון – היועץ העסקי שלך

תוכנה בעברית (RTL) למשרד ייעוץ עסקי. בלי build framework: HTML/JS/CSS סטטיים, ו-Firebase להתחברות ולשמירה בענן.

| מצב | מתי | מה יש |
|---|---|---|
| **מקומי** | `firebase-config.js` ריק (ברירת מחדל), או פתיחה כקובץ `file://` | הכול נשמר ב-localStorage, בלי התחברות. שוק הייעוץ הוא הדגמה. |
| **ענן** | `firebase-config.js` מלא | התחברות (מייל או שם משתמש + סיסמה / Google), שמירה וסנכרון חי בין מכשירים, שוק ייעוץ משותף בין משתמשים. |

## מודולים
1. **ניהול משרד** – לקוחות, פרויקטים, משימות, רישום שעות וחשבוניות.
2. **אבחון עסקי** – שאלון 20 שאלות, SWOT, דוח והמלצות.
3. **תוכנית ותחזית** – תזרים 1–36 חודשים, נקודת איזון, גרף, CSV.
4. **אפיון אישי** – שאלון ל**מייסד/ת, שותף/ה או מטפל/ת** ב-8 שלבים: פרטים וקשר; רקע מקצועי (התמחויות, השכלה, שפות); עסק וקהל (קהל יעד, ערוצים, הכנסה ויעד, מחיר, תקציב); מטרות ויעדים מספריים; חוזקות; סגנון ואישיות (ערכים, אנרגיה, זמנים, למידה); חסמים, תמיכה רצויה, מוכנות ומועד התחלה; שאלות לתפקיד. רוב השדות בבחירה מרובה ← תוכנית אישית ל-90 יום, שאפשר להפוך בלחיצה למשימות עם תתי-משימות ותאריכים.
5. **שוק ייעוץ** – בקשות והצעות מחיר. בענן: הצעות המחיר גלויות רק לבעל הבקשה ולמגיש.

## הפעלת Firebase (חד-פעמי)
> **פרויקט חדש ונפרד.** אל תשתמש בפרויקט של Rate Desk (`loanbid`): `firebase deploy` של הכללים יחליף את הכללים שלו.

1. ב-[console.firebase.google.com](https://console.firebase.google.com) צור פרויקט, והוסף **Web app**.
2. **Build → Authentication → Sign-in method**: הפעל *Email/Password* ו-*Google*.
   **Settings → Authorized domains**: הוסף את הדומיין שבו האתר יעלה.
3. **Build → Firestore Database**: צור מסד נתונים (מצב production).
4. העתק את הגדרות ה-Web app (`apiKey`, `authDomain`, `projectId`, `appId`) אל `firebase-config.js`. אלה מזהים ציבוריים, לא סודות.
5. בנה ופרוס:
   ```bash
   npm i -g firebase-tools && firebase login
   firebase use --add            # בחר את הפרויקט
   python3 build.py              # מייצר dist/index.html
   firebase deploy --only firestore:rules,hosting
   ```
   אפשר גם לפרוס את `dist/index.html` לכל אחסון סטטי (Netlify וכד'). הכללים חייבים לעלות דרך `firebase deploy --only firestore:rules`.

Google Sign-In והתחברות בכלל לא עובדים מ-`file://`; יש להגיש את האתר ב-https או ב-`localhost`.

## מבנה הנתונים ואבטחה (`firestore.rules`)
- `workspaces/{uid}` – כל נתוני המשרד של המשתמש (JSON אחד, עד ~900KB) ותווית (מייל / שם משתמש). הבעלים קורא וכותב; **מנהל קורא בלבד**.
- `admins/{uid}` – מסמך שמסמן מנהל. נוצר **ידנית בקונסולה בלבד**; הכללים אוסרים על כל לקוח ליצור, לשנות או למחוק אותו.
- `requests/{id}` – בקשת ייעוץ. כל משתמש מחובר קורא; הבעלים יוצר ורשאי רק לסמן `accepted`.
- `requests/{id}/quotes/{consultantUid}` – הצעת מחיר אחת לכל יועץ. נקראת רק ע"י בעל הבקשה והיועץ עצמו; אי אפשר להגיש הצעה לבקשה של עצמך או אחרי שנבחרה הצעה.

נבדק מול Firestore Emulator: 32 בדיקות כללים (בעלות, זיוף זהות, הפרדת הצעות מחיר, שדות לא חוקיים) ובדיקת קצה-לקצה בדפדפן עם שני משתמשים (הרשמה, שמירה אחרי רענון, סנכרון בין מכשירים, פרסום בקשה, הגשה ואישור הצעה, מחיקה).

## אפיון אישי: איך התוכנית נבנית
כללים קבועים בקוד (`app.js`: `P_BASE`, `P_GAP`, `P_GOAL_ACT`, `buildProfile`), בלי AI ובלי שליחת נתונים החוצה:
- **תבנית לפי תפקיד** (7 פעולות בסיס לכל תפקיד), בארבעה שלבים: יסודות (14 יום), הקמה (30), צמיחה (60), סקירה (90).
- **התאמה לתשובות התפקיד** (למשל מייסד בשלב רעיון מקבל בדיקה משפטית; שותף בלי הסכם כתוב מקבל את "לנסח הסכם" כפעולה ראשונה; מטפל בלי הדרכה מקבל "למצוא מדריך").
- **פערים:** לשתי המיומנויות הנמוכות ביותר, פעולות חיזוק; לחוזקה הבולטת, פעולה למינוף.
- **מטרות:** פעולה לכל אחת משלוש המטרות שנבחרו (בעדיפות גבוהה).
- **תשובות אישיות:** פער הכנסה מתורגם למספר פגישות במחיר שלך; כל חסם, ערוץ חסר או תמיכה מבוקשת מוסיפים פעולה; מועד ההתחלה מזיז את כל התאריכים; מוכנות גבוהה מוסיפה פעולות ונמוכה מצמצמת. בשוויון עדיפות, פעולה שנגזרת מהתשובות קודמת לתבנית הכללית.
- **עוד פעולות מומלצות:** מה שלא נכנס בגלל מגבלת הזמן מוצג בנפרד, וכל פעולה ניתנת להוספה לתוכנית בלחיצה.
- **זמן פנוי:** עד 5 שעות בשבוע ← 6 פעולות, עד 15 ← 10, יותר ← 14 (±2 לפי מוכנות). פעולות חיוניות נשמרות ראשונות, וסקירת 90 היום תמיד נכללת.
לשינוי הניסוחים או הוספת תפקיד עורכים את הטבלאות האלה.

## שאלון ללקוחות בקישור
בלשונית **אפיון אישי** → כרטיס "שליחת שאלון ללקוחות": מסמנים "פתוח", מדביקים קישור לקביעת פגישה (Calendly, יומן Google וכו', חייב `https://`) ושומרים. מתקבל קישור `…/#intake/<uid>` עם כפתורי וואטסאפ ומייל.
- הלקוח ממלא את אותו שאלון בן 8 השלבים **בלי להירשם**, ובסיום מועבר אוטומטית לקישור קביעת הפגישה.
- התשובות נשמרות ב-`intakes/{id}`; כשאתה מחובר הן נקלטות **אוטומטית** כאפיון עם תוכנית (תגיות "חדש" ו"מולא ע״י הלקוח"), ונמחקות מהתיבה רק אחרי שהאפיון נשמר בענן.
- אבטחה: כל אחד יכול רק **ליצור** שאלון, ורק לטופס פעיל; קריאה ומחיקה לבעלים (או מנהל) בלבד; גודל מוגבל; שדה מלכודת לבוטים. מומלץ להפעיל גם Firebase App Check נגד ספאם.
- **חובה לפרסם את `firestore.rules` העדכני** כדי שזה יעבוד.

## מנהל (הרשאה לראות את כל הפרויקטים)
מנהל מקבל לשונית **ניהול**: סיכום של כל המשתמשים, טבלת *כל הפרויקטים* עם שם הבעלים, ו"פתח הכול" לכל משתמש (לקוחות, פרויקטים, משימות, שעות, חשבוניות, אבחונים). **קריאה בלבד**, גם בכללי האבטחה, ולא רק בממשק.

**הדרך הקצרה:** ב-`firestore.rules` מוסיפים את המייל (או שם המשתמש כ-`שם@username.invalid`, באותיות קטנות) לרשימה `adminEmails()`, ומפרסמים את הכללים (Rules → Publish). זה הכול, בלי UID ובלי מסמכים.

דרך חלופית, בלי לגעת בכללים:
1. המשתמש נרשם לאתר ונכנס פעם אחת.
2. ב-Firebase Console → **Authentication → Users** מעתיקים את ה-**User UID** שלו.
3. **Firestore Database → Data → Start collection** (או Add document אם קיים) → Collection ID: `admins` → Document ID: **ה-UID** → מוסיפים שדה כלשהו (למשל `note` = שם) → Save.
4. המשתמש מרענן את האתר ורואה את הלשונית. להסרה מוחקים את המסמך.

שים לב: מנהל רואה נתונים אישיים של לקוחות של כל המשתמשים. מומלץ ליידע את המשתמשים בתנאי השימוש. עדכון הכללים נדרש (Rules → Publish) לפני שזה עובד.

## שם משתמש
במסך הכניסה אפשר להזין מייל **או שם משתמש** (3–30 תווים באנגלית, ספרות, `.` `_` `-`; לא רגיש לאותיות גדולות). Firebase מזהה לפי מייל, ולכן שם משתמש ממופה בצד הלקוח לכתובת פנימית `שם@username.invalid` שאינה נשלחת לשום מקום. אין בכך צורך בהגדרה נוספת ב-Firebase.
- **איפוס סיסמה במייל** זמין רק למי שנרשם עם מייל. למשתמש עם שם משתמש: Firebase Console → Authentication → Users → ⋮ → *Reset password*, או מחיקה ויצירה מחדש.
- אי אפשר לשנות שם משתמש אחרי ההרשמה (הוא מזהה החשבון).

## אמינות השמירה
- כל שינוי נכתב קודם לעותק מקומי בדפדפן (סינכרונית), ורק אחר כך נשלח לענן. אם הדף נסגר או רועננן לפני שהשמירה הסתיימה, השינויים משוחזרים בכניסה הבאה ונשמרים.
- עדכון שמגיע מהענן לא דורס שינויים מקומיים שעוד לא נשמרו; עדכון ישן (אותה גרסה) מתעלמים ממנו.
- אם השרת דוחה את הכתיבה מופיע באנר אדום והאתר ממשיך לנסות אוטומטית עד שמצליח.

## מגבלות ידועות
- סנכרון בין מכשירים הוא "הכותב האחרון מנצח" על כל מסמך המשרד. עריכה בו-זמנית (בטווח של שנייה) משני מכשירים תדרוס. עריכות עוקבות מסתנכרנות בזמן אמת.
- מחיקת בקשה מוחקת את ההצעות שעליה מהצד של הלקוח; אם החיבור נופל באמצע, ייתכנו הצעות יתומות (לא נגישות לאיש).
- אין התראות מייל על הצעה חדשה או על בחירה בהצעה.
- החשבונית היא מסמך הדגמה, לא חשבונית מס רשמית.
